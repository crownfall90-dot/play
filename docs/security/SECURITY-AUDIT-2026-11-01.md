# Отчёт по аудиту безопасности (Security Audit 2026-11-01)

Проведён комплексный аудит безопасности кодовой базы Puzzlegrad: клиентского кода (`web/game.html`, `src/`), правил базы данных (`docs/firebase-rules.json`), сетевого протокола комнат и защиты данных игроков.

---

## 1. Резюме выявленных уязвимостей и исправлений

| ID | Область | Описание | Критичность | Статус |
|---|---|---|---|---|
| **SEC-01** | Клиент / DOM | Потенциальный XSS через удалённое сообщение `start` и `data-addf` (`m.seats`, `x.uid`, `#podium`, `#bd`) | **Высокая** (High) | ✅ **Исправлено**: строгая очистка `clean(x.name)`, валидация `x.col` / `x.fig`, санитизация `x.uid` через `[^\w-]`. |
| **SEC-02** | Firebase Rules | Чтение PIN-кода стейджинга неавторизованными пользователями (`config/testerPin` имел `.read: true`) | **Средняя** (Medium) | ✅ **Исправлено**: доступ на чтение и запись ограничен только администраторам. |
| **SEC-03** | Экономика / Промокоды | Повторное использование промокодов при очистке `localStorage` и утечка кодов | **Средняя** (Medium) | ✅ **Исправлено**: добавлено серверное дерево `promo_claims/$code/$uid` с однократной записью (`!data.exists()`). |
| **SEC-04** | База данных / DoS | Неограниченный рост комнат (`/rooms`), устаревших записей `presence` и логов | **Низкая** (Low) | ✅ **Исправлено**: разработан скрипт автоматической очистки `scripts/cleanup-db.py` (удаление комнат >7 дней, presence >24ч, ошибок >30д). |
| **SEC-05** | Клиент / Античит | Проверка целостности кошелька и блокировка DevTools/инспектора | **Информационная** | ✅ **Проверено**: `walletSig` защищает баланс золота, блокировки F12/контекстного меню активны. |

## 2. Подробное описание уязвимостей

### SEC-01: Удалённая инъекция через имена и идентификаторы игроков (XSS)
- **Механизм**: Хост сетевой комнаты отправляет сообщение `start` с массивом `m.seats`. Ранее `m.seats.map(x => ({name: x.name, ...}))` передавал сырую строку имени без предварительной очистки. При отображении результатов на подиуме (`#podium`) и в таблице (`#bd`) значение подставлялось в `.innerHTML`. Кроме того, в списке игроков лобби атрибут `data-addf="${x.uid}"` не экранировал спецсимволы в `uid`.
- **Вектор атаки**: Злоумышленник мог отправить сетевое сообщение с `name: "<img src=x onerror=...>"` или манипулированным `uid` с кавычками, выполнив произвольный JavaScript в контексте других участников комнаты.
- **Исправление**:
  1. В обработчике `startGame` применён `clean(x.name) || 'Игрок'` и приведение `x.uid` через `String(x.uid).replace(/[^\w-]/g, '').slice(0, 64)`.
  2. Цвета и фигурки строго валидируются по белым спискам `validCol(x.col)` и `FIGS[x.fig]`.
  3. В `renderResults` вывод имен на подиум и в таблицу защищён вызовом `clean(p.name)`.
  4. В лобби `data-addf` использует отфильтрованный `uid`.

### SEC-02: Утечка PIN-кода стейджинга через REST API
- **Механизм**: Узел `/config/testerPin` в `docs/firebase-rules.json` имел правило `".read": true`. Любой пользователь мог выполнить неаутентифицированный GET-запрос `https://<project>.firebaseio.com/config/testerPin.json` и узнать актуальный PIN для прохода через заглушку стейджинга.
- **Исправление**:
  - Правило `.read` для `testerPin` изменено на `"auth != null && root.child('admins').child(auth.uid).val() === true"`.
  - Заглушка стейджинга опирается на доверенный fallback или защищённый запрос.

### SEC-03: Повторная активация промокодов и учёт на сервере
- **Механизм**: Ранее активация промокода фиксировалась только локально в массиве `wallet.promos`. Сбросив кэш браузера или удалив ключ из `localStorage`, игрок мог активировать один и тот же промокод из базы неограниченное число раз, накручивая золото.
- **Исправление**:
  - В `docs/firebase-rules.json` добавлено правило для `promo_claims`:
    ```json
    "promo_claims": {
      "$code": {
        "$uid": {
          ".read": "auth != null && auth.uid === $uid",
          ".write": "auth != null && auth.uid === $uid && !data.exists()",
          ".validate": "newData.hasChildren(['t']) && newData.child('t').val() === now"
        }
      }
    }
    ```
  - В функции `redeemPromo` перед начислением золота выполняется проверка `/promo_claims/$code/$uid.json`. Если промокод уже использовался этим аккаунтом, запрос отклоняется. При успешной активации создаётся серверная запись с отметкой времени.

### SEC-04: Очистка устаревших данных (S-3)
- **Механизм**: Комнаты `/rooms` и сообщения `/rooms/$code/msgs` не имели встроенного времени жизни (TTL), что приводило к неограниченному накоплению данных в Realtime Database.
- **Исправление**:
  - Создан скрипт `scripts/cleanup-db.py`, поддерживающий безопасный предварительный просмотр (`--dry-run`) и боевой запуск (`--execute`).
  - Удаляет комнаты, не имевшие активности более 7 дней, маркеры присутствия старше 24 часов и телеметрию ошибок старше 30 дней.

---

## 3. Инструкция для владельца проекта
1. Скопируйте обновлённое содержимое `docs/firebase-rules.json` в **Firebase Console → Realtime Database → Правила** и нажмите **Опубликовать**.
2. Для регулярной чистки базы настройте запуск скрипта `scripts/cleanup-db.py --execute` в ночном cron-расписании на сервере / в GitHub Actions.
